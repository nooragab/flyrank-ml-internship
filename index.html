Which Pages to Review First

A validated model for prioritizing content refresh decisions, built on a 100,000-page slice of a 79-million-row search warehouse.

Nour Ragab · Refresh / Content Opportunity Scoring lane · March–April 2026 data

Abstract

Content teams cannot review every page they own, so this work asks which pages to look at first, using a page's observable March 2026 search signals to predict whether its visibility declines into April. A transparent baseline rule is compared against logistic regression and random forest classifiers under a client-grouped, held-out validation split. In this run, both trained models scored higher than the baseline at Precision@20 and Precision@50, though each figure rests on a small number of pages and should be read as directional. A separate diagnostic comparison suggests an ungrouped train/test split can substantially inflate reported precision, which is why validation design matters as much as model choice. The output is a reason-coded, human-reviewed action queue, framed as decision support rather than a causal or automated system.

Introduction

A content team with dozens or hundreds of pages and limited editorial hours cannot review everything with equal attention. Some pages are worth revisiting — refreshed facts, tightened titles, expanded thin sections — before they lose the visibility they already have. The problem this work addresses is narrow and practical: given a page's recent, observable search performance, which pages deserve review first?

The decision this supports belongs to a content editor or SEO lead operating under limited weekly review capacity. A wrong recommendation has a real but bounded cost — time spent reviewing a page that did not need it, or a genuinely declining page left unreviewed a week longer. This is a decision-support problem, not a fully automated one: the model orders a queue, and a person decides what to do with each entry.

Data

This study uses the FlyRank/internship-warehouse release on Hugging Face (build flyrank_pseudonymized_warehouse_release_v20260703), a pseudonymized snapshot of real search performance data. The full release holds 78.8 million daily fact rows (fact_content_daily_performance) and 519,606 content items (dim_content), across 104 clients.

Tables used

  • dim_content.parquet — content metadata: word count, creation and last-update dates.
  • fact_content_daily_performance/month=2026-03/ and month=2026-04/ — daily Google Search Console facts, filtered to rows with confirmed GSC data availability.

Date windows

March 2026 serves as the feature window; April 2026 serves as the label window. This is a genuine past-to-future split — the label is never computed from data the model could see at prediction time.

Scope and exclusions

The working slice is restricted to pages with at least 100 March impressions, yielding 100,893 page-rows across 43 clients. GA4 engagement signals (sessions, scroll depth, engagement rate) were excluded to keep the feature set to five core, easily-auditable signals; this is a scoping choice for this iteration, not a data-availability limit. No FlyRank product decision flags (health score, priority score, action type) exist in this release, so none required stripping. Every identifier used — client and content IDs — is a pseudonymized hash; no raw client names, domains, URLs, or search queries appear anywhere in this work.

Methodology

Baseline

A transparent, hand-written rule serves as the bar to beat: score = impressions × is_stale × ctr_gap, where is_stale flags pages unchanged for 90+ days and ctr_gap is how far a page's click-through rate sits below its position tier's average.

Label

is_declining_next_month = 1 if a page's April impressions fall below its March impressions, else 0. Because the label window is strictly after the feature window, this avoids the within-month proxy weakness identified earlier in this project's data contract.

Features

Five signals, each knowable before the decision point: monthly impressions, average search position, click-through rate and its gap to the position-tier average, a staleness flag, and word count.

Models

Logistic regression and random forest classifiers were trained on the same feature set as the baseline, so the comparison is apples-to-apples.

Validation design

Pages are split by GroupShuffleSplit, grouped by client, so no single client's pages appear in both the training and test sets. This choice was checked with a separate diagnostic run (notebook w06): scoring a random forest on an ungrouped random split gave a Precision@50 of 0.98, against 0.72 on the client-grouped split in that run. That large gap is consistent with the model recognizing client-specific patterns rather than learning something general. Those two figures come from that earlier run and are not the figures in the results table below. All results in this paper use the grouped split.

Leakage audit

Every feature was checked against three questions: is it computed strictly before the decision point, does its measurement window overlap the label window, and is it a rebuilt product decision flag? All eight model inputs passed — each is computed from March data alone or from static content metadata, and no product flags exist in this dataset to leak in.

Results

Precision@K measures how many of a ranking's top K picks were genuinely declining pages — the metric that matches how a review queue is actually used.

MethodPrecision@20Precision@50
Baseline rule0.600.66
Logistic regression0.850.88
Random forest0.850.78

For context, about 66% of pages in the full working dataset declined from March to April, so a random ranking would be expected to score roughly 0.66 on Precision@K. The baseline rule's Precision@50 of 0.66 is therefore close to chance, while the trained models scored higher in this run. Because Precision@50 is computed over only 50 pages, differences of a few hundredths between methods fall within ordinary sampling variation, and the difference between the two trained models should not be read as meaningful. The supported reading is directional: the trained models scored higher than the baseline here. It is not evidence that the gap holds at every queue depth, in every month, or for every client segment.

On reproducibility: when the underlying notebook was rerun, the exact precision values changed from run to run (Precision@50 for the same models ranged from roughly 0.66 to 0.88 across reruns). Adding a fixed row ordering to the query did not remove the variation, and the cause was not fully isolated. The table above comes from one run, with its input data saved locally at the time. That saved file is a data file and is deliberately kept out of the public repository, so a reader rerunning the notebook should expect values that differ somewhat from those shown. The direction of the findings was consistent across the runs observed: the trained models scored above the baseline, and an ungrouped split scored far above a grouped one.

Limitations

  • Observational, not causal. This work shows association between observable signals and future decline. It does not show that refreshing a flagged page causes recovery — that would require a controlled experiment.
  • Single month pair. The model is trained on one March→April transition. Performance on other months, or through a strong seasonal shift, is untested.
  • 43 clients. Validation was not performed on client types or industries outside this training population.
  • Thin-traffic risk. Some flagged pages carry as few as 100–200 monthly impressions; model confidence is weaker there, and these cases are flagged separately for reviewer caution.
  • Metric variability. Exact precision values changed across reruns and the cause was not isolated. The figures reported here are from a single run, so small differences between methods should not be over-interpreted.

All claims in this paper use observed, measured, directional, or decision-support language. Nothing here claims to reverse-engineer a Google ranking factor, nor to prove that any specific action causes a specific outcome.

Ranked Recommendations

The validated random forest model scores each held-out page; each score is paired with a reason code and a concrete next action, so a reviewer always knows why a page was flagged.

high_risk_underperformer
Action: review_for_refresh. Model probability ≥ 0.65. The strongest signal in the queue — work this tier first.
visible_ctr_gap
Action: review_metadata. A large click-through gap at a decent search position. Route to a title/snippet review rather than a full content rewrite.
low_confidence
Action: monitor_only. Borderline model probability. Lowest cost-benefit ratio per review — batch-monitor rather than review individually.

Human review is required before acting

Before acting on any recommendation, a reviewer should confirm the page is still live and business-relevant, check whether the flagged issue still holds on the live page, and rule out an explanation the model cannot see — a seasonal campaign ending, a sibling page absorbing demand, or a site migration.

What should never be automated: auto-publishing content changes from the model's score alone; auto-deleting or de-indexing low-confidence pages; treating the model's probability as a guaranteed forecast; or applying this queue to clients outside its training population without re-validation.

Monitoring and retrain triggers

The queue should be treated as stale, and the pipeline re-run, if: Precision@50 on a fresh month's held-out data drops meaningfully below this run's baseline; the feature distribution shifts materially from the March training snapshot; a structurally new client segment appears; or more than roughly three months pass since the last retrain.
